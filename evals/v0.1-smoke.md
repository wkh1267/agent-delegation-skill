# Delegent V0.1 Smoke Evaluation

Use these scenarios to validate orchestration behavior before adding automatic
Worker affinity or trajectory escalation.

For every run, record:

```text
workflow:
expected_owner:
actual_owner:
expected_memory_action:
actual_memory_action:
lead_duplicated_worker_exploration: yes | no
handoff_sufficient: yes | no
escalation_correct: yes | no | n/a
workflow_completed: yes | no
notes:
```

## 1. Approved implementation

Invocation:

```text
$delegent $implement

Architecture is already approved. Implement a change that touches several source
and test files, run the relevant tests, and preserve the existing public API.
```

Expected:

- Lead keeps fixed decisions and mutation boundaries.
- repository exploration, implementation, tests, and routine debugging go to a build Worker.
- the same Worker is reused through implementation → test → debug.
- Lead receives a compact handoff and performs final acceptance.

## 2. Architecture decision

Invocation:

```text
$delegent $implement

Before implementation, decide whether a new durable state belongs in the public
schema or an internal scheduler structure.
```

Expected:

- the architecture/schema decision stays with Lead.
- implementation may be delegated only after the decision is fixed.

## 3. Broad repository exploration

Invocation:

```text
$delegent $research

Trace how a feature works across an unfamiliar repository and identify the
smallest safe implementation seam.
```

Expected:

- broad reading and dependency tracing go to a plan Worker.
- Lead does not duplicate the broad exploration.
- Worker returns evidence and a compact conclusion.

## 4. Trivial local work

Invocation:

```text
$delegent $implement

Change one already-known constant in the currently loaded file and run its one
known focused test.
```

Expected:

- Lead may keep the task because dispatch overhead exceeds the context savings.
- Delegent should not delegate mechanically just because `implement` is active.

## 5. Same-subsystem follow-up

First run a context-heavy implementation in one subsystem using a titled Worker
session. Then invoke:

```text
$delegent $implement

Make a follow-up change in the same subsystem that depends on the previous
Worker's repository understanding.
```

Expected:

- session discovery goes through `nemotron-worker.ps1 sessions`.
- the matching `delegent:<project>:<scope>:<role>` session is considered.
- the existing Worker is reused only after scope/role fit and staleness are checked.

## 6. Independent review

Invocation:

```text
$delegent $code-review

Review the completed change for correctness and spec compliance.
```

Expected:

- prefer a fresh Worker when delegated review is useful.
- do not reuse the implementation Worker merely because its session is available.
- Lead retains final acceptance.

## 7. Hard decision escalation

Give a Worker an approved implementation task that later reveals a required
public API, schema, security, or irreversible behavior change.

Expected Worker response:

```text
DECISION_NEEDED
Question:
Evidence:
Options:
Recommendation:
Confidence:
```

Expected orchestration:

- Worker stops instead of guessing.
- Lead resolves the consequential decision.
- the same Worker resumes when continuity remains useful.

## 8. Stale persistent Worker

Create a reusable Worker, change relevant repository code outside that session,
then issue a follow-up task.

Expected:

- Worker uses only allowed read-only Git operations when resynchronizing in plan mode.
- relevant changes are inspected before old working memory is trusted.
- whole-repository rereading is avoided unless the changes invalidate the old model.

## 9. Unrelated subsystem

After a persistent Worker exists for subsystem A, invoke a task for unrelated
subsystem B.

Expected:

- do not reuse A merely to avoid creating a session.
- start a fresh Worker if delegation is useful.

## 10. Context Firewall

Use a task that produces substantial logs, search output, and failed debugging
attempts inside the Worker.

Expected:

- raw trajectory stays inside Worker context.
- Lead receives only the required handoff fields and evidence.
- Lead does not ask for full logs/source dumps unless a specific verification gap requires them.

## Observed V0.1 smoke findings

### Worker execution and compact handoff

Observed with the `plan` Worker on Nemotron 3 Super:

- the Worker attempted `ls -la`, which was correctly denied by the `plan` bash policy;
- the Worker recovered using allowed read tools and completed the inspection;
- the Worker returned a compact handoff rather than a repository/source dump;
- the first handoff contained all required fields.

Result: **PASS** for Worker execution, permission enforcement, recovery, and Context Firewall output behavior.

### Same-session follow-up

A related follow-up was sent to the same OpenCode session. The Worker identified that the prior repository understanding remained relevant and recommended reusing the existing context rather than starting fresh.

Result: **PASS** for session continuity and reuse-policy behavior.

One follow-up handoff omitted `CHANGES`, `TESTS`, and `RISKS`; this is a prompt-adherence defect because the Worker contract requires all fields, using `none` when genuinely inapplicable.

Result: **PASS WITH CONTRACT DEFECT** for handoff completeness.

### Staleness / targeted resynchronization

The reused Worker performed a targeted Git resynchronization using read-only commands including `git status`, `git log`, and `git diff`, and avoided rereading the whole repository.

Result: **PASS** for read-only Git resynchronization primitives and targeted refresh behavior.

However, the Worker approximated its baseline with a relative revision such as:

```text
git diff HEAD~5..HEAD -- spec.md
```

That is not a reliable staleness baseline. It answers what changed in an arbitrary recent commit window, not what changed since this Worker last synchronized. It also inspected only `spec.md` while making a repository-level conclusion, so the evidence scope was narrower than the conclusion.

Result: **PARTIAL** for exact staleness detection.

Required follow-up for V0.2:

- persist the exact `last_sync_commit` for every reusable Worker;
- compare `last_sync_commit..HEAD` before reuse;
- inspect the complete changed-path set before concluding whether the Worker's prior model remains trustworthy;
- then reread only relevant changed files unless those changes invalidate broader repository understanding.

This smoke finding validates that `last_sync_commit` is a functional requirement, not only a future optimization. Heuristics such as `HEAD~N` must not be treated as equivalent to an exact Worker baseline.

## Pass condition

V0.1 is ready for broader use when the scenarios above consistently demonstrate:

- workflow semantics are preserved;
- high-impact decisions stay with Lead;
- context-heavy execution moves to Workers;
- session reuse is deliberate rather than automatic;
- independent work can get fresh context;
- hard escalation works;
- the Context Firewall is maintained;
- final acceptance remains with Lead.
